* Development Workflow

Emacs is the editing, navigation, diagnostics, and review surface. Codex runs in
Ghostty inside a project-scoped tmux session. The browser stays separate for
documentation and application testing.

** Start a project

From niri, press =Mod+P= and select a top-level project from =~/work=. The
launcher starts three apps; Niri window rules place them on the existing
workflow workspaces:

- =build=: GUI Emacs opened through =emacsclient=.
- =ops=: Ghostty attached to the project's tmux session.
- =scratch=: the configured browser using the project-only
  =dev.vals.ProjectBrowser= app ID.

Normal browser windows do not match the project rule, so documentation windows
can remain in =write=.

Start the terminal workflow directly when the full desktop preset is not needed:

#+begin_src sh
  dev-session ~/work/project
  dev-session --launch ~/work/project
#+end_src

Use the direct command for projects outside =~/work= or nested below another
project directory. The launcher and the Emacs =C-c x a= command both delegate
terminal startup to =dev-session=.

Sessions are named =dev-<project>= and contain two permanent tmux windows:

- =agent=: Codex, rooted at the project directory.
- =shell=: an independent shell for builds, tests, logs, and Git commands.

Each =dev-loop= task adds a window named after its task slug. The window closes
when its agent exits and can be recreated with =dev-loop resume=.

With the =C-x= tmux prefix, use =C-x a= for the agent and =C-x s= for the shell.

** Work in Emacs

Project commands use Emacs's built-in =C-x p= prefix:

- =C-x p p=: switch project.
- =C-x p f=: find a project file.
- =C-x p b=: switch project buffer.
- =C-x p g=: search the project.
- =C-x p c=: compile from the project root.
- =C-x p k=: kill project buffers.

Use =C-c g d= to review tracked changes against =HEAD= with Difftastic.

Java buffers use =java-ts-mode= when the Home Manager managed tree-sitter
grammar is available. Eglot starts JDT LS directly; use standard Xref and Eglot
commands for navigation and refactoring, and =C-x p c= for tests and builds.

Git Gutter marks changed lines in file buffers. Use =C-c g p= and =C-c g n= to
visit the previous or next hunk, and =C-c g h= to preview the current hunk.
Magit refines changed words within every displayed diff hunk.

Use =F10= for buffers, =Shift+F10= for recent files, =C-.= for contextual
Embark actions, and =C-x g= for Magit.

** Work with agents

Use =C-c x= to move explicit context from Emacs to the terminal agent:

- =C-c x a=: open the current project's Codex session in Ghostty.
- =C-c x f=: copy the current project-relative =file:line=.
- =C-c x r=: copy the active region with its file and line range.
- =C-c x p=: open a personal task contract.
- =C-c x j=: open a job task contract with a ticket field.
- =C-c x s=: archive and submit the current task contract.

Task contracts are submitted only by =C-c x s=; normal save and close commands
never start an agent. Press =Escape= to delete and cancel an unsubmitted draft.
Submitted contracts remain under =~/tasks/<project>/=.

A normal change loop is:

1. Check =git status= and create a checkpoint when the change is substantial.
2. Open =C-c x p= or =C-c x j= and fill the task contract.
3. Add precise file or region context from Emacs when it reduces ambiguity.
4. Submit with =C-c x s= and review the agent's read-only investigation and plan.
5. Unlock write access and explicitly approve implementation in the task session.
6. Inspect edits in Emacs or Magit instead of accepting the summary alone.
7. Run focused tests, then the broader project checks from the =shell= window.
8. Review the final diff and separately approve =dev-loop finish=.

The contract keeps =Agent= and =Title= at the top; job contracts also keep
=Ticket=. State one concrete outcome, only the context that changes the answer,
task-specific constraints, and observable completion checks.

Choose model and permissions inside Codex with =/model= and =/permissions=.
Do not hard-code broad permissions into the project launcher.

** Maintain this configuration

After editing the repo:

#+begin_src sh
  make check
  make sync
#+end_src

=make check= validates managed files and shell syntax. =make sync= installs the
repo-managed Emacs, tmux, niri, helper configuration, and shared
=manage-makefile= skill into the Codex and Claude skill directories.

* Isolated agent task loop

=dev-loop= is a small wrapper around Git worktrees, Codex or Claude, and
GitLab merge requests. It gives the agent an isolated task checkout while the
operator keeps control of review and integration. The shared =manage-makefile=
skill keeps project Makefiles thin and requires every target to document itself
through generated =make help= output.

The workflow is intentionally supervised. Every new or resumed task session
starts read-only: the agent investigates and presents a plan before the
operator grants write access and explicitly approves implementation. After the
agent edits and runs checks inside its worktree, it must present the result and
receive separate approval before committing, merging, pushing, or opening a
merge request. This is roughly autonomy level 2, with limited level 3 task
execution inside the worktree. It does not run unattended or merge GitLab work
automatically.

** Install

Apply this repository normally:

#+begin_src sh :results output silent
  make apply
#+end_src

This installs =dev-loop= in =~/bin=, =glab= through Home Manager, and the shared
=manage-makefile= skill for Codex and Claude. Both agent CLIs must already be
installed and authenticated. For GitLab work, authenticate =glab= as well:

#+begin_src sh :results output silent
  glab auth status
#+end_src

Run =make doctor= to check the required commands.

** Start a task

From Emacs, use =C-c x p= for personal work or =C-c x j= for ticketed job work.
Fill =Agent= and =Title= in the template, plus =Ticket= for job work, then submit
with =C-c x s=. Emacs stores it under =~/tasks/<project>/= with private
permissions; =dev-loop= validates and reads the metadata.

=templates/agent-task.md= provides the same contract as a standalone Markdown
file for later use as an Obsidian template. It is personal by default; add a
=Ticket: VID-1132= line above =Title= for job work.

** Use the template with Obsidian

Copy the template into the templates directory of the relevant Obsidian vault:

#+begin_src sh :results output silent
  cp templates/agent-task.md "/path/to/vault/Templates/Agent task.md"
#+end_src

Enable Obsidian's core =Templates= plugin and select that directory as the
template folder. For each task, create a note and insert =Agent task=.

For personal work, fill =Agent= and =Title= and leave the template without a
=Ticket:= line. For job work, add the ticket above =Title=:

#+begin_src markdown
  Agent: codex
  Ticket: VID-1132
  Title: Support new protocol
#+end_src

Fill =Outcome=, =Context=, =Constraints=, and =Done when=, then save the note.
From the clean primary checkout of the project, submit its absolute path:

#+begin_src sh :results output silent
  cd ~/work/project
  dev-loop start-task "/path/to/vault/Tasks/support-new-protocol.md"
#+end_src

=dev-loop= reads =Agent=, =Ticket= when present, and =Title= from the note. It
keeps the note unchanged, creates the adjacent worktree, and opens the named
task window in the project's tmux session. The Obsidian note remains the task
contract used by =dev-loop resume= and can be kept as the permanent record.

Run =start= from the clean primary checkout of a repository:

#+begin_src sh :results output silent
  dev-loop start codex "Improve cache invalidation"
  dev-loop start claude "Improve cache invalidation"
#+end_src

For job work that needs a GitLab merge request, include the ticket:

#+begin_src sh :results output silent
  dev-loop start codex --ticket VID-1132 "Support new protocol"
#+end_src

Tickets must use uppercase project keys and a number, such as =VID-1132=. The
tool creates:

- branch =agent/vid-1132-support-new-protocol=;
- worktree =<repo-parent>/.worktrees/<repo>/vid-1132-support-new-protocol=; and
- local Git metadata recording the agent, starting commit, target branch,
  ticket, and title.

The selected agent opens in that worktree with the shared workflow skill and
read-only access. It investigates the repository, presents a decision-complete
plan, and waits. For Codex, use =/permissions= to select workspace-write and
then explicitly approve the plan. For Claude, accept the native plan-mode
transition and explicitly instruct it to implement. The agent then implements
the approved plan, runs the repository's relevant checks, reviews the final
diff, and reports assumptions and risks. Security-sensitive, infrastructure,
concurrency, public API, destructive, unusually large, or materially uncertain
changes also receive a read-only review from the other agent when available.
The project tmux session keeps its generic =agent= and =shell= windows and adds
a window named after this task.

If the agent exits before the task is complete, resume it from the task
worktree:

#+begin_src sh :results output silent
  dev-loop resume
#+end_src

Every resumed session starts read-only again. Review its continuation plan,
unlock write access, and approve implementation again; approval is not carried
between sessions.

** Approve and finish

Review the agent's result. If it is acceptable, explicitly approve finishing in
the same agent session.

For a personal task without =--ticket=, =dev-loop finish= commits the work and
fast-forwards the original local branch. It refuses to integrate if that branch
has advanced or its checkout is dirty.

For a ticketed task, the agent passes an approved handoff containing =Summary=,
=Verification=, =Assumptions=, and =Risks= to =dev-loop finish=. The tool commits,
pushes, and opens a GitLab merge request with the exact title:

#+begin_example
  [VID-1132] - Support new protocol
#+end_example

The merge request remains for human review and merge; auto-merge is never
enabled.

Codex may request permission when finishing needs network access or must update
the primary checkout. Claude runs with a stricter sandbox and may be unable to
perform the final integration step. In that case, leave the reviewed task
worktree unchanged and run =dev-loop finish= there from the normal terminal.

** Personal terminal session

The whole personal loop starts and ends in the primary checkout:

#+begin_example
  $ cd ~/Github/project
  $ git status --short
  $ dev-loop start codex "Remove duplicate cache entries"
  Preparing worktree (new branch 'agent/remove-duplicate-cache-entries')
  Started agent/remove-duplicate-cache-entries in tmux window
  remove-duplicate-cache-entries (...).

  # Continue in the selected remove-duplicate-cache-entries tmux window.
  # Codex investigates and presents an implementation plan without editing.
  > /permissions
  # Select workspace-write.
  > Approved. Implement the plan.
  # Codex implements the change, runs checks, and presents the final diff.
  > Approved. Finish it.
  ...
  Integrated agent/remove-duplicate-cache-entries into main.
  Cleanup: dev-loop clean agent/remove-duplicate-cache-entries

  $ dev-loop clean agent/remove-duplicate-cache-entries
  Deleted branch agent/remove-duplicate-cache-entries (...).
#+end_example

If the agent cannot perform the approved finish from its sandbox, open the
reported worktree in the normal terminal, run =dev-loop finish= there, then
return to the primary checkout for cleanup.

** Job terminal session

The ticket selects the GitLab flow and determines the merge-request title:

#+begin_example
  $ cd ~/work/project
  $ git status --short
  $ dev-loop start codex --ticket VID-1132 "Support new protocol"
  Preparing worktree (new branch 'agent/vid-1132-support-new-protocol')
  Started agent/vid-1132-support-new-protocol in tmux window
  vid-1132-support-new-protocol (...).

  # Continue in the selected vid-1132-support-new-protocol tmux window.
  # Codex investigates and presents an implementation plan without editing.
  > /permissions
  # Select workspace-write.
  > Approved. Implement the plan.
  # Codex implements the change, runs checks, and presents the MR handoff.
  > Approved. Create the merge request.
  ...
  Creating merge request for agent/vid-1132-support-new-protocol into main
  [VID-1132] - Support new protocol

  # Later, process one round of reviewer feedback from the task worktree.
  $ cd ../.worktrees/project/vid-1132-support-new-protocol
  $ dev-loop feedback
  ...

  # After the merge request is merged, clean up from the primary checkout.
  $ cd ~/work/project
  $ dev-loop clean agent/vid-1132-support-new-protocol
  Deleted branch agent/vid-1132-support-new-protocol (...).
#+end_example

The agent generates the required =Summary=, =Verification=, =Assumptions=, and
=Risks= description during the approved finish. The operator reviews and merges
the resulting MR in GitLab.

** Merge-request feedback

After reviewers add comments, run one feedback pass from the task worktree:

#+begin_src sh :results output silent
  cd ../.worktrees/project/vid-1132-support-new-protocol
  dev-loop feedback
#+end_src

The same agent inspects unresolved discussions, handles clear in-scope requests,
runs checks, pushes the fixes, and replies to the addressed threads. Ambiguous,
architectural, security-sensitive, conflicting, or scope-expanding requests are
returned to the operator. A feedback invocation is one pass; there is no
background polling.

** Clean up

After personal work is integrated or the GitLab merge request is merged or
safely closed, run this from the primary checkout:

#+begin_src sh :results output silent
  dev-loop clean agent/vid-1132-support-new-protocol
#+end_src

Cleanup refuses active task windows, unexpected worktree paths, unintegrated
personal branches, and open merge requests. Archived task contracts are never
removed automatically.

** Recovery and inspection

Worktrees and branch metadata are ordinary Git state:

#+begin_src sh :results output silent
  git worktree list
  git config --get-regexp '^branch\.agent/.*\.dev-loop-'
#+end_src

If a personal target branch advances, rebase the task onto the new target,
update its =dev-loop-base= metadata to that target commit, rerun affected checks,
and review and approve the refreshed result before finishing. =dev-loop=
reports this recovery rule when it detects an advanced target.

Use =dev-loop help= for the compact command reference.
